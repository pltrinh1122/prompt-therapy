# Plan #9 — product development play-book: the lifecycle of Prompt Therapy as a product and as a service

base commit: 5d61d9353f88c47e6d2c254478fcaa38f4f12fa5

## Definition of done (proposed, from provenance #9 entries 1 and 2)
1. One overall play-book, `product-development`, for the whole lifecycle of Prompt Therapy: building, testing,
   deploying **and operating it as a service** (entry 2), and evolving it from what operation teaches.
2. One play-book per lifecycle phase, `product-specifications` among them. That play-book creates and maintains the PRD,
   the Architecture and the UX/UI Design so that they stay coherent and do not drift. A mechanical check fails a push
   that lets them drift.
3. Every judgement action in every play-book cites a `dmc` record, which an existing core or craft record may be
   (Rule-13: reuse over authoring). The dmc guard resolves every citation, and the craft's test fails any judgement
   with no citation.
All three are judged together by #9's done-`Y`.

## Intent as read
The operator wants Prompt Therapy run as a product with a repeatable lifecycle, not phase by phase as P1–P3 were
planned. The play-books are the procedure; each decision inside them is a `dmc` record, so a decision is made the
same way every time and can be audited. Entry 2 widens "deploying" to running the service: watching it, responding to
incidents and user requests, enforcing retention, managing cost and provider outages, and retiring it.
The play-books describe the work; they authorize nothing. Each phase's work is still a d-work row, with its own
plan-`Y` and done-`Y` (Rule-3). Deploying and running the service reach the world, so each of those acts is asked
under the Rule that owns it (Rule-8 for host actions, Rule-11 for a release, Rule-19 for a server instance).

## Where it lives
Everything goes in the Tended craft `crafts/prompt-therapy/` (craft zone, one PR), following the cabinet craft's
pattern: `playbooks/`, `dmc/`, and a craft rule as owner. This plan names no core change, because a craft may carry
play-books and dmc records (`dyad/dmc/schema.md`, "Where records live"). Every new record's `dyad:home` is its
play-book, so it is the **master** of its decision. Its play-book cites it as `dmc:<id>` and states none of its
outcomes in full (schema, "Master or index").

## Mutation
### A. Play-books (`crafts/prompt-therapy/playbooks/`)
Each play-book has the same sections: Trigger, Steps, Judgements (a table of judgement → `dmc:<id>`), Questions (what
is asked of the operator, and under which Rule), Evidence (what its d-work's completion reply cites).

| play-book | phase | judgement actions → dmc (new unless marked) |
|---|---|---|
| `product-development.md` | the whole lifecycle: Specify → Build → Test → Select provider → Deploy → Operate → Evolve, then back to Specify | which phase a prompt or a finding belongs to → `dmc:lifecycle-phase`; whether a phase's exit gate holds → `dmc:phase-gate`; which version a change makes → `dmc:product-version` |
| `product-specifications.md` | Specify: create and maintain PRD, Architecture, UX/UI Design | which document owns a statement → `dmc:spec-home`; the order of edits across the three and the code → `dmc:spec-change-order`; whether the set has drifted → `dmc:spec-drift`; whether a change needs the operator's acceptance or is editorial → `dmc:spec-acceptance` |
| `build.md` | Build | whether a code change needs a spec change first → `dmc:spec-first`; import or author → `dmc:import-criteria` (syseng, reused); which test a module maps to → `dmc:test-mapping` (syseng, reused) |
| `test.md` | Test, P2's adversarial tests included | which level a test belongs to (unit, conversation, adversarial) → `dmc:test-level`; what a fixture may hold (synthetic, or the operator's own prompts cited by provenance; never a user's words) → `dmc:fixture-source`; what a failing test means (product defect, spec gap, fixture defect, canon moved) → `dmc:test-failure` |
| `provider.md` | Select provider (P3), and re-select | which provider serves (cheapest that passes the adversarial tests, on a dated price comparison), and when to re-select → `dmc:provider-choice` |
| `deploy.md` | Deploy | where the service runs → `dmc:deploy-target`; whether a build may be deployed → `dmc:deploy-readiness`; each deploy step's class → `dmc:host-action-class` (core, reused); whether deploying is Done → `dmc:deployed-done` (core, reused) |
| `operate.md` | Operate the service | what a signal is (health failing, an incident, a user's request, retention due, cost over budget, provider down, canon moved) → `dmc:operate-signal`; a service level missed and what follows → `dmc:service-level`; a user's request (delete, complaint, safety concern) → `dmc:user-request`; when a conversation is expired or deleted → `dmc:retention` (mechanical: `scripts/store.py`); roll back or fix forward → `dmc:rollback`; spend against budget → `dmc:service-cost`; a provider outage → `dmc:provider-outage`; whether something is an incident and where it is recorded → `dmc:incident`, `dmc:incident-record-home` (core, reused); whether to retire the service → `dmc:service-retire` |
| `evolve.md` | Evolve: what operation teaches goes back into the specs | where a finding goes (spec change here, a canon hand-up to dyad-system, a bug, out of scope) → `dmc:feedback-route`; the split of a hand-up → `dmc:intake-split` (core, reused) |

That makes 8 play-books and 20 new dmc records, and 7 reused ones. Running the service is ongoing. So `operate.md`
names its server instance's run-book and health command (Rule-19), and the read-only health checks the automaton
sweep runs. Monitoring itself opens no row (Rule-3, Ledger); a signal that needs an act opens one.

### B. The anti-drift check
1. `docs/prd.md` gains stable requirement ids (`PRD-1` …) on the statements it already holds. No requirement is
   changed, and `dmc:spec-acceptance` classes an ids-only change as editorial. `docs/architecture.md` and `docs/ux.md`
   cite the ids each section realizes.
2. A craft guard, `guards/specs.py` (entity `spec`; guard contract `crafts/sysarch/rules/guards.md`), fails a push in
   any of these cases:
   - a PRD id that neither the architecture nor the UX design cites;
   - a citation of an id the PRD does not hold;
   - an id defined twice;
   - a spec document that names no `PRD-` id at all.
   Its test is `tests/guards/test_specs.py`. So every push judges what `dmc:spec-drift` decides mechanically. The
   rest, whether a cited section really realizes its requirement, stays inference, and the play-book states that.
3. `tests/test_playbooks.py` checks, for every play-book, that each row of its Judgements table cites a `dmc:<id>`,
   and that it has Trigger, Steps, Judgements, Questions and Evidence.

### C. Craft shape
- `rules/product-development.md`: a Tended Rule stating the lifecycle and the spec set. It is the `dyad:owner`
  (`prompt-therapy:product-development`) of every new record. `rules/README.md` lists it.
- `vocabulary/CRAFT.md`: `product specifications`, `lifecycle phase`, `exit gate`, `requirement id`, `service
  level`. None of these is an Agent term.
- `falsification/rules/product-development.md`: the rule's falsification record.
- `README.md` lists `playbooks/` and `dmc/`; `VERSION` goes from 0.1.0 to 0.2.0.

## Falsification
- "Play-books belong in the core, `dyad/playbooks/`": refuted. They are about one product, so they fall under `dmc:intake-split`'s instance
  or craft class, never upstream core. The cabinet craft already carries its own play-books and records.
- "Every judgement cites a dmc can be checked only by reading": survives, scoped. Whether a step is a judgement stays
  inference. A Judgements table per play-book makes the claim checkable row by row, the dmc guard resolves every
  citation, and the test fails a row with none.
- "Drift can only be prevented by review": refuted for the trace (B2 makes it mechanical), and it survives for
  meaning. Whether a section really realizes a requirement is inference, and the play-book says so and asks for it
  at each spec change.
- "Adding ids to accepted documents is a requirement change": refuted. No statement changes, and the done-`Y` shows
  the diff.
- "Operate is just Deploy plus a health check": refuted by entry 2. Running a service brings service levels, user
  requests, retention, cost, provider outages, incidents, rollback and retirement. Each is a judgement with its own
  record.
- "Twenty new records restate existing ones": survives, scoped. Seven decisions reuse a core or syseng record. The
  rest decide questions no record here asks; each record lists the reused ones it relies on in `dyad:alsoIn`.
- Presence: no other live session's files overlap `crafts/prompt-therapy/`.

## Revision 2 (asked 2026-11-15, after the push hook refused)
**What happened.** The plan-`Y` was recorded and the mutation built as written on `p9/playbooks`:

The craft's own checks passed: the trace, the dmc guard over 198 records, and 30 craft tests. The push hook refused

- `dyad/tests/test_check_trigger.py`: every registry label needs a row in `dyadlib.CHECK_INPUTS`, a core table no
  craft can contribute to.
- `crafts/sysarch/tests/test_project_entities.py`: a hard-coded set of craft guard paths.

So a downstream system cannot add a craft guard without editing the installed core and the installed sysarch craft
(`dmc:install-refusal`). Rule-11 property 2 says a core-owned table holding craft-varying data accepts a craft-shipped
contribution, so this is an upstream defect.

**Revision.** The trace check moves from a guard to a script and its test:
- `crafts/prompt-therapy/scripts/specs.py` (same functions, no guard contract);
- `crafts/prompt-therapy/tests/test_specs.py`, which runs it on the live specifications.

The suite runs on every code push (Rule-12 property 2), so a broken trace still fails the push, which is what B2
promised. `playbooks/product-specifications.md` and the rule name the new path, and `dmc:spec-drift`'s implementation
moves with it. Nothing else changes. The upstream defect is reported to you as a candidate hand-up and is not sent
without your words.
