# Plan #1 — P1 infrastructure: PRD, Architecture and UX/UI Design accepted; service skeleton; offline whole-conversation harness

base commit: 4d7e785313363273a4d0fce2e30612911280993a

## Definition of done (proposed: the phase plan's, `site/lean-canvas/prompt-therapy.md` in dyad-system, branch `d-work/702-phase-plan`)
1. A PRD, an Architecture and a UX/UI Design, each accepted by the operator.
2. A service skeleton.
3. A test harness that runs a whole conversation against fixtures with no live provider.
All three judged together by #1's done-`Y`; the documents are also shown for a read before any code is built on them.

## Intent as read
Prompt Therapy v1.0 is a user-agent chat service. A user brings what they saw an AI agent do. The agent matches it to
dyad-system's symptom canon, walks its why-tree with them (asking their why, offering causes only as hypotheses),
reaches the anchor, says what helps, and asks consent before keeping the symptom. Every page and first message says it
is no therapy and no professional advice. Conversations live in the service's own store, never in a repository, with
their own retention and deletion: the reason this is its own dyad system (D1, D5).

## The first decision: where the service lives
No zone of this system holds product code (Rule-1's table: agent, workstation, preferences, craft, infra; `site/` and
`.claude/` are infra, and an unclassified path is refused). Three homes were weighed:
- **a Tended craft, `crafts/prompt-therapy/`** (craft zone) — chosen. Rule-11 lets a craft hold rules, docs, scripts,
  templates, guards and tests, and its tests run in the suite (Rule-12), so the harness is part of every push's check.
  It carries no instance state (Rule-11 property 1), which fits: conversations never enter a repository. Its `VERSION`
  and `MANIFEST.md` come from `dyad craft new prompt-therapy` (the craft run-book's `new`).
- a new zone for product code — refuted: the zone table is core (`dyad/guards/infra/containment.py`), so it is an
  upstream change, and it would wait on a release.
- a separate repository — refuted for P1: the phase plan puts the code, the harness and the adapters in this system.
The documents live in the same craft, `crafts/prompt-therapy/docs/`, so the whole of P1 is one zone.

## Mutation (order: required — documents before code)
Stage A, the documents, one craft-zone PR:
1. `docs/prd.md` — users and the problem; the walk (match, why-tree, anchor, what helps, consent to keep); the
   no-therapy line and where it shows; what is out of scope (diagnosis, naming a person, keeping without consent: the
   three things P2's harness fails); retention and deletion of conversations; the hand-up of a consented,
   de-identified symptom and the Intake gap that still stands before it.
2. `docs/architecture.md` — one service: a conversation engine running the walk as a state machine; a canon reader
   that reads dyad-system's canon (`site/lean-canvas/symptoms.md` and the why-trees) at a pinned commit, read-only;
   one provider interface with a fake adapter only (P3 adds real ones); a conversation store behind an interface, its
   retention and deletion stated; no conversation, key or user datum in any repository. Kernel: Python 3.12, stdlib.
3. `docs/ux.md` — the chat: first message with the no-therapy line; each walk step's prompt and the user's choices;
   how a cause is offered as a hypothesis; the consent question; deletion on request.
Stage A ends with a read of the three documents in chat. It asks nothing; a correction is an amend.

Stage B, the code, one craft-zone PR:
4. `dyad craft new prompt-therapy` (run-book `craft new`), then the skeleton under `crafts/prompt-therapy/`: the walk
   engine, the canon reader against a pinned fixture copy, the provider interface and its fake adapter, the store
   interface with an in-memory store.
5. The harness: `tests/` running whole conversations from fixture files, provider faked, asserting each walk ends at
   an anchor, offers causes only as hypotheses, and keeps nothing without consent. Run by the suite.

## Falsification
- "A craft is reusable practice, not a product": survives, scoped. Rule-11 defines a craft by its shape (one root,
  `VERSION`, no instance state), not by its subject; this one may never be installed elsewhere, and nothing requires it.
- "The canon may not be read by a service in another system": refuted. The phase plan places the canon in dyad-system
  and says the service reads it and never writes it; dyad-system is public.
- "Fixtures of real symptoms belong in P1": refuted. P2 owns the operator's symptom prompts as fixtures; P1's harness
  runs on synthetic fixtures only.
- "Document acceptance needs three more questions": refuted. One done-`Y` judges the whole definition of done; Stage
  A's read lets a correction land before code depends on it, at no extra question.
- Rule-13 (import over author): no third-party import in P1; stdlib only, so no manifest row.
