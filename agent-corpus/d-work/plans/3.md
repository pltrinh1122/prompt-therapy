2. A dated price comparison, with its sources.

## Intent as read
A real model words the walk's replies. The engine keeps choosing every state, and the never-rule checks keep running
on every outgoing line, whatever the model writes. The bar is P2's 42 members, the same set the fake provider passes.

- **The key.** One credential for `api.anthropic.com`, asked through the credential request form. You enter it there;
  I never see or store it.
- **Sending content to the provider.** The adversarial set is sent to the provider's API: your public prompts, read

- **Spend.** At most **US$10** in total across every evaluation run, stopped before the bound. The estimate is about
  $0.05 on Haiku and about $3 on Opus for one full pass, at the cached list prices below.
- **One reversible host action.** `pip install anthropic==2.8.0` into this session's Python (undo: `pip uninstall
  anthropic`), with a change-log row.

## Revision 4 (the operator's prompt, provenance #3 entry 6, with a screenshot of the console's "Connect to the Claude API" dialog)
The operator asked for a decision record for how Prompt Therapy authenticates to the Claude API: for testing now, and
for the production host later. The dialog offers four ways: your own machine (`ant` CLI sign-in), cloud or
Kubernetes, a CI pipeline (the first three need no key), and somewhere else (an API key).

**The record, `dmc:provider-auth`** (`crafts/prompt-therapy/dmc/provider-auth.jsonld`, homed in `playbooks/provider.md`
and cited by `playbooks/deploy.md`, judged by inference)

Decides: how does a Prompt Therapy run authenticate to the Claude API?

Inputs:
- where the code runs;
- whose run it is: a person's evaluation or the service;
- whether a long-lived secret can be kept safely there;
- whether the adapter supports the method;
- which account and workspace the spend lands on.

Outcomes:

| outcome | when | then |
|---|---|---|
| **sign-in** (your own machine) | a person runs it on their own machine: an evaluation, a test, a demo | `ant auth login` once. The adapter takes the short-lived token from `ant auth print-credentials --access-token` and sends it as `Authorization: Bearer` with `anthropic-beta: oauth-2025-04-20`. No key is stored. The spend lands on that person's workspace. |
| **workload identity** (cloud or Kubernetes) | the service runs on a cloud host or cluster with an identity provider | A federation rule and a service account, with a workload token exchanged for a short-lived API token; no stored secret. The SDK does the exchange by itself; a stdlib adapter writes it. The production default. |
| **CI federation** (CI pipeline) | an unattended job calls the API, such as a scheduled adversarial run | The pipeline's OIDC token is federated the same way; no stored secret. |
| **API key** (somewhere else) | none of the three can run there | A key scoped to its own workspace, with a spend limit, kept only as that host's secret, rotated, and never in a repository, a file or the chat. |

- **Precedence:** a method with no stored secret comes before a key. The service in production never runs on a
  person's sign-in, because that ties the service to one person's account, billing and departure.
- **Default:** sign-in for a person; workload identity for the service.

**Applied now.** P3's evaluation runs on the operator's own machine, which is sign-in.
- `scripts/provider.py` reads `ANTHROPIC_AUTH_TOKEN` and sends it as `Authorization: Bearer` with the OAuth beta
  header. `ANTHROPIC_API_KEY` stays accepted, so the record's key outcome works too.
- The ops script gets the token with `ant auth print-credentials --access-token` before each model's run (the token
  is short-lived) and never writes it anywhere. It needs `ant` signed in (`ant auth login`), no key.

**Applied later.** The production host is decided at Deploy by `dmc:deploy-target`, and its authentication by this
record. If it is a cloud host, workload identity needs a token exchange: either the SDK, which the core refuses today
as a craft import (an upstream hand-up candidate), or a stdlib exchange written then. Deploy's plan states which.

**Mutation added:**
- the record;
- the citations in `provider.md` and `deploy.md`;
- the adapter's bearer path and its test;
- the ops script's token step.

The rest of revisions 1 to 3 stands. If you choose sign-in, you need no API key at all.

## Revision 5 (provenance #3 entries 8 and 9: the operator asked that the evaluation run in a Docker container, falsified, and the operator's Y to write it)
**The falsification, in short.**
- **Interference.** The script as written interferes with the operator's own clone: it checks out `p3/ops`, adds a
  git worktree, and writes `prompt-therapy.canon` into the clone's shared `.git/config`.
- **What a container isolates.** Files, Python and git state, but only if it clones fresh inside and mounts nothing
  from the operator's workspace.
- **Credentials.** They stay self-contained if the sign-in stays on the host and only a fresh, short-lived token
  enters each run, with `--rm`.
- **What a container does not isolate.** The API workspace's rate limits and spend, shared with any other work using
  that workspace (a dedicated `ant` profile and workspace is the remedy), or the host's CPU and network.
- **Docker.** It is a new dependency, and so a manifest row.

**Revision.** `workstation-corpus/ops/3-h1-provider-evaluation.sh` is rewritten, still unrun:
1. The operator fetches it without touching their clone:
   `git fetch origin p3/ops && git show origin/p3/ops:workstation-corpus/ops/3-h1-provider-evaluation.sh > /tmp/3-h1.sh`.
2. The script builds an image `pt-eval:3-h1` from `python:3.12-slim` with `git` and `ca-certificates`. The Dockerfile
   is piped into `docker build -`, so there is no file to track.
3. For each model it runs `docker run --rm -e ANTHROPIC_AUTH_TOKEN pt-eval:3-h1 <model> <budget>`, with the token
   taken fresh from `ant auth print-credentials --access-token` on the host just before.
   - Inside, the entrypoint clones prompt-therapy at the adapter commit and dyad-system, checks the pin, sets
     `prompt-therapy.canon` inside the container, and runs `evaluate.py`.
   - The container mounts no volume; its output goes to stdout.
4. The host keeps only the log, `${WORK:-$HOME/pt-eval}/evaluation.log`, and the image. Undo: `docker rmi pt-eval:3-h1`
   and `rm -rf "$WORK"`. The postcondition and the "already satisfied" re-run are unchanged.
5. An exported `ANTHROPIC_API_KEY` remains the fallback, passed the same way.

**Also in the workstation-zone PR:**

  row for Docker: library, observed on the operator's machine, profile `operating`, replacement the bare-host run of

- the H1 change-log row's action, which names the container.

**Limits, stated in the script's header:** the shared workspace limits and spend, and a token visible to
