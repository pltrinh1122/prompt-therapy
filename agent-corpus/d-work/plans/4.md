# Plan #4 — spawn play-book carries the disposition that completes a spawn: hand-up to dyad-system

## Definition of done (proposed)
A hand-up, ready for the operator to send to dyad-system, that (a) amends the craft-instantiation play-book's
"Steps: another dyad system" with a spawn definition of done and the disposition that carries it, and (b) reports the
defect that blocks a fresh system's first guarded push. Sent only on the operator's `Y`; the build is dyad-system's row.

## Intent as read
The operator asks that the spawn play-book carry forward the disposition a spawn needs to reach its definition of
done, so a new system's first unit is not stopped to ask again for acts the spawn's plan-`Y` already authorized. The
play-book is the core craft's (`dyad/playbooks/craft-instantiation.md`), installed here unmodified and authored in
dyad-system, which this unit may not write. By `dmc:intake-split` the change is **upstream core**: every installing
operator spawns the same way. Editing the installed copy here would make the core tree modified (`dmc:install-refusal`)
and would not reach dyad-system. So this row writes the hand-up, and the operator refines the definition of done.

## Falsification
- "Edit the play-book here instead": refuted. It is the installed core; a local edit marks it modified and never
  reaches the authoring system.
- "The prompt's spawn plan-`Y` already covers all six acts, so no amendment is needed": survives, scoped. A plan-`Y`
  binds only what its plan names (Rule-2), and the play-book names only `system-new`, a registry row, craft installs
  and one ledger row, so acts 2 to 6 were not named.
- "Seeding `main` directly is a ratification event": refuted for a ledger-only commit (Rule-2, Not ratification).
- Item 3 as stated in place of fixing item 2: survives only together with it; either alone unblocks the first push,
  so both are offered and dyad-system chooses.
